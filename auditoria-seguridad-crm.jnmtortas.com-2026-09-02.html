Resumen ejecutivo

El CRM Nexora CRM desplegado en crm.jnmtortas.com expone su API completa sin ningún tipo de autenticación. Cualquier persona con acceso a Internet puede leer y modificar todos los datos del negocio (contactos con datos personales, empresas, oportunidades de venta, cotizaciones, contratos, notas internas, tickets) y, además, generar claves de API válidas con permisos arbitrarios para acceder también a la API pública. Se encontraron secretos de firma expuestos y credenciales de demostración por defecto activas. Adicionalmente, se confirmó un SSRF legible que permite al servidor hacer peticiones a la red interna: se alcanzó el IMDS de Azure (169.254.169.254) y el backend interno localhost:3006 directamente (saltándose Cloudflare), leyendo las respuestas. La brecha es total a nivel de aplicación y alcanza la red interna del backend.

Analogía

Imagina un edificio de oficinas de ventas (el CRM) con la recepción de cristal a la entrada. En condiciones normales, un visitante se identifica, le dan una llave de su despacho y solo ve lo suyo. En este edificio, la puerta de entrada no tiene cerradura: cualquiera entra, abre los archivadores de todos los clientes (con cédulas, teléfonos y direcciones), lee las notas internas del equipo, las cotizaciones y los contratos. Peor aún: en el mostrador hay una máquina que imprime llaves maestras con los permisos que tú quieras, y el vigilante (el sistema de "quién es de qué empresa") solo se fía de lo que el visitante le diga de palabra. Nadie pide credencial, nadie registra quién entra, y las claves de las cajas fuertes están pegadas con un post-it en la pared.

Vulnerabilidades críticas

Crítica · API sin autenticación (lectura)

Lectura no autenticada de todos los datos del CRM

Cualquier endpoint de la API BFF (/api/*) responde con 200 OK y datos reales sin requerir token. Se expone información personal de contactos (nombres, cédulas, email, teléfono, dirección, fecha de nacimiento), empresas con NIT, oportunidades, cotizaciones, contratos, tareas, notas internas, tickets de soporte, campañas, formularios, productos, equipos y pipelines.

GET /api/contacts HTTP/1.1
Host: crm.jnmtortas.com
→ HTTP 200  (lista completa de contactos con PII)

GET /api/companies → 200 (empresas + taxId)
GET /api/pipelines/deals → 200 (oportunidades)
GET /api/quotes → 200 (cotizaciones + términos)
GET /api/contracts → 200 (contratos)
GET /api/notes → 200 (notas internas)
GET /api/tickets → 200 (tickets de soporte)

Fix: Exigir un JWT válido en todos los endpoints BFF (guard global de NestJS), derivando el tenantId del token y no del cliente.

Crítica · Escritura no autenticada

Creación, modificación y borrado sin autenticación

Los métodos POST, PUT/PATCH y DELETE también funcionan sin token. PoC: se creó una clave de API (respuesta 201) y se borró (200 success:true) — la operación se revirtió limpiamente.

POST /api/developer/api-keys
Content-Type: application/json
{"name":"audit-test-reversible","scopes":["contacts:read","deals:read"]}
→ HTTP 201  { "rawKey": "nex_live_..." }

DELETE /api/developer/api-keys/b9ac31ab-...
→ HTTP 200  { "success": true }

Fix: Aplicar autorización por rol/permiso en escritura y auditoría de cambios.

Crítica · Generación de claves de API con permisos arbitrarios

Un anónimo puede emitir claves de API y acceder a la API pública /v1

El endpoint POST /api/developer/api-keys permite crear claves nex_live_... con scopes arbitrarios (ej. contacts:write, deals:write, webhooks:manage). Con la clave generada se accedió a la API pública /api/v1/*, que de otra forma exige la clave.

POST /api/developer/api-keys  (sin token)
→ 201 { "rawKey": "nex_live_71d3..." }

GET /api/v1/contacts
Authorization: Bearer nex_live_71d3...
→ HTTP 200  (datos de contactos)

Fix: Proteger la creación de claves tras autenticación y limitar los scopes al rol del usuario.

Crítica · Secretos expuestos

Secreto de firma de webhooks y token de verificación de Facebook en texto plano

Los endpoints de listado devuelven secretos operativos que un atacante puede reutilizar para falsificar eventos firmados.

GET /api/developer/webhooks → HTTP 200
{ "secret": "whsec_99a8b7c6d5e4f3a2b1c099887766554433221100aabbccddeeff001122334455", ... }

GET /api/integrations/facebook/status → HTTP 200
{ "webhookSecret": "fb_verify_090274df", ... }

Fix: No devolver nunca secretos por API; exponer solo keyPrefix/hash y rotar los secretos comprometidos.

Crítica · SSRF legible hacia la red interna

El servidor ejecuta peticiones arbitrarias a direcciones internas y devuelve la respuesta

Los webhooks salientes no validan la URL de destino. Creando un webhook con una URL interna y disparando un evento de prueba, el backend realiza la petición y almacena la respuesta en responseBody, que puede leerse sin autenticación. Se confirmó:

  • Alcance al IMDS de Azure (http://169.254.169.254/...) → respuesta XML del servicio de metadatos. El backend corre en Microsoft Azure.
  • Alcance al backend interno (http://localhost:3006/api/companies) → respuesta de validación de la API interna, eludiendo Cloudflare.
POST /api/developer/webhooks
{"url":"http://169.254.169.254/metadata/instance?api-version=2021-02-01","events":["contact.created"]}
→ 201 (URL interna aceptada, sin validación SSRF)

POST /api/developer/webhooks/dispatch {"event":"contact.created"}
GET  /api/developer/webhooks/{id}/deliveries
→ responseBody: {"error":"Bad request: . Required metadata header not specified"}

POST .../dispatch → webhook a http://localhost:3006/api/companies
→ responseBody: {"error":"validation_error","details":[{"path":"name","message":"Required"}]}

Nota: el IMDS de Azure exige la cabecera Metadata: true, que el cliente de webhooks no envía, por lo que no se pudo extraer el token de identidad administrada por este vector (control mitigador). El alcance a red interna y la lectura de respuestas quedan demostrados. Un vector SSRF con control de método/cabeceras (GET + headers) derivaría en compromiso del entorno cloud.

Fix: Validar y bloquear destinos SSRF (IPs privadas/link-local 169.254.0.0/16, 127.0.0.0/8, 10/8, 172.16/12, 192.168/16, nombres de host internos), permitir solo HTTPS a dominios públicos y aplicar allow-list.

Vulnerabilidades altas

Alta · Aislamiento multi-tenant roto

El tenant se elige con una cabecera del cliente sin validación de pertenencia

El backend determina el inquilino a partir de la cabecera X-Tenant-Id enviada por el cliente. Sin la cabecera devuelve el tenant demo por defecto; con una cabecera arbitraria devuelve datos de ese tenant (o vacío si no existe). No hay verificación de que el solicitante pertenezca al tenant, por lo que en un despliegue multi-tenant real cualquier cliente podría leer los datos de otro conociendo su ID.

GET /api/contacts                       → datos del tenant ...000001 (default)
GET /api/contacts -H "X-Tenant-Id: 9999..." → {} (el servidor acepta el ID sin validar)

Fix: Derivar el tenant del JWT verificado (claim tenantId), nunca de una cabecera de confianza del cliente.

Alta · Credenciales por defecto válidas

Cuenta demo activa con credenciales conocidas

El login con demo@nexoracrm.com / Password123! devuelve un JWT válido (HS256, sin claim de rol). La documentación de la API publica estas credenciales de ejemplo y están vivas.

POST /api/auth/login
{"email":"demo@nexoracrm.com","password":"Password123!"}
→ HTTP 201 { "accessToken": "eyJhbGciOiJIUzI1NiI..." }

Fix: Deshabilitar/rotar cuentas demo en producción y no publicar credenciales reales en la documentación.

Alta · Documentación de API pública

Swagger/OpenAPI completo expuesto en /api/docs

El spec OpenAPI 3.0 embebido revela la totalidad de la superficie (más de 150 endpoints, controllers, modelos y ejemplos), facilitando enormemente la enumeración y explotación.

Fix: Deshabilitar Swagger en producción o protegerlo tras autenticación interna.

Alta · Revelación del framework

Cabecera X-Powered-By: Next.js

Revela la tecnología del servidor y ayuda a un atacante a seleccionar exploits específicos.

Fix: Eliminar la cabecera X-Powered-By.

Alta · Ausencia de Content-Security-Policy

Sin CSP

No hay política de contenido, lo que amplía el impacto de cualquier inyección (XSS) futura.

Fix: Definir una CSP restrictiva sin unsafe-inline.

Alta · Mass assignment en integraciones

Un POST con cuerpo vacío habilita y activa una integración sin credenciales

POST /api/integrations/{provider} (saveConfig) acepta un cuerpo arbitrario y, con {}, puso la integración en isConfigured:true, isEnabled:true. Se revirtió con DELETE /api/integrations/{provider}.

POST /api/integrations/WHATSAPP_CLOUD  (body {})
→ 201 {"ok":true}  →  la integración queda isConfigured:true, isEnabled:true

DELETE /api/integrations/WHATSAPP_CLOUD  → 200 {"ok":true}  (revertido)

Fix: Validar la configuración requerida por proveedor; no permitir habilitar sin credenciales válidas.

Vulnerabilidades medias

Media · Sin HSTS

Falta Strict-Transport-Security

No se fuerza HTTPS a nivel de navegador, habilitando ataques de downgrade.

Fix: Strict-Transport-Security: max-age=31536000; includeSubDomains.

Media · X-Frame-Options: SAMEORIGIN

Protección anti-iframe parcial

Se usa SAMEORIGIN en lugar de DENY (o frame-ancestors).

Fix: X-Frame-Options: DENY + CSP frame-ancestors 'none'.

Media · Sin rate limiting evidenciado

Sin throttling en la API

Durante la auditoría se realizaron numerosas peticiones sin observar 429, Retry-After ni bloqueos. No se evidenció limitación de tasa (sin forzar bursts).

Fix: Añadir rate limiting por IP y por clave en el edge (Cloudflare) y en la API.

Media · Revelación de infraestructura interna

Host interno y dominio de producción expuestos

Las respuestas revelan http://localhost:3006 (backend) y crm.nexora.app (producción), información útil para reconocimiento.

Fix: No exponer URLs internas en configuraciones visibles.

Media · SSRF potencial vía webhooks/integraciones

URLs de webhook controlables sin auth

POST /api/developer/webhooks y endpoints de integración aceptan URLs hacia las que el servidor realiza peticiones salientes; sin autenticación, un atacante podría apuntarlas a servicios internos. (No explotado contra terceros por ética; validado a nivel de diseño.)

Fix: Validar destinos (bloqueo de IPs privadas/metadatos) y exigir auth.

Media · Endpoint MCP sin autenticación

Servidor MCP (Model Context Protocol) expuesto

GET /api/mcp/sse entrega un sessionId a cualquiera sin autenticación, y POST /api/mcp/messages acepta mensajes JSON-RPC. La enumeración de herramientas falló por un error del servidor (stream is not readable), posible bug de implementación del transporte SSE.

Fix: Proteger el endpoint MCP tras autenticación y corregir el manejo del stream.

Media · Registro de auditoría sin IP real

El trail inmutable registra 127.0.0.1 como IP de origen

GET /api/audit/logs es accesible sin auth y las entradas muestran ipAddress: "127.0.0.1", lo que indica que no se propaga la IP real del cliente tras Cloudflare, inutilizando el rastro forense y permitiendo impunidad.

Fix: Confiar en CF-Connecting-IP / X-Forwarded-For solo desde el proxy, y registrar la IP real.

Media · Token VoIP emitido sin autenticación

Generación de token Twilio Voice sin auth

POST /api/voip/token devuelve un token sin requerir sesión. En este entorno Twilio está mockeado (AC_MOCK_ACCOUNT_SID), pero en producción revelaría el account SID y permitiría iniciar llamadas.

Fix: Exigir autenticación y limitar la identidad al usuario autenticado.

Media · Motor de workflows acepta acciones SSRF sin validar

La acción WEBHOOK admite URL/método/cabeceras arbitrarias

El motor de automatización acepta nodos {action:"WEBHOOK", config:{url, method, headers, body}} con destinos internos (ej. 169.254.169.254 con Metadata: true) sin validación SSRF. En este despliegue la ejecución parece ser un stub (no llegó a hacer la petición HTTP real — un POST de prueba a localhost:3006/api/tags no creó el registro), pero la configuración se acepta y persiste, lo que representa un riesgo SSRF latente.

POST /api/automation/workflows
{"stepsGraph":[{"id":"1","type":"ACTION","action":"WEBHOOK",
  "config":{"url":"http://169.254.169.254/metadata/instance?api-version=2021-02-01",
            "method":"GET","headers":{"Metadata":"true"}}}]}
→ 201 (config SSRF aceptada)

Fix: Validar destinos de acciones HTTP (bloquear IPs privadas/link-local) y restringir métodos/cabeceras.

Plan de acción

  • Ahora: Activar autenticación global en toda la API BFF y /v1 (guard JWT obligatorio).
  • Ahora: Bloquear SSRF en webhooks/integraciones (allow-list, denegar IPs privadas/link-local).
  • Ahora: Rotar el webhook secret, el token de Facebook y deshabilitar la cuenta demo.
  • Hoy: Derivar tenantId del JWT y eliminar la confianza en X-Tenant-Id.
  • Hoy: Quitar Swagger/API docs de producción y X-Powered-By.
  • Esta semana: Añadir CSP, HSTS, X-Frame-Options DENY y rate limiting.
  • Antes de lanzar: Revisión de autorización por rol en escritura y SSRF en webhooks/integraciones.

Implicaciones legales

Los datos expuestos incluyen datos personales (nombres, cédulas, emails, teléfonos, direcciones). Aunque el dataset observado es de demostración/seed, el mecanismo compromete datos reales en producción. Según el régimen aplicable al operador (Colombia — Ley 1581 de 2012, y RGPD/LOPD si trata datos de la UE), una brecha de esta naturaleza puede implicar sanciones, notificación obligatoria a autoridades y afectados, y responsabilidad civil. El secreto de webhook comprometido también puede afectar a integraciones de terceros.
